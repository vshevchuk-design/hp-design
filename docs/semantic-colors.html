Semantic colors

tokens/semantic/color.tokens.json · aliases tokens/primitives/color.tokens.json · generated

surface

Page structure — canvas, cards/panels, recessed fields, backdrops. page and default are both literal white deliberately — cards read as 'raised' via border.default, not a background shift. Use default/page for the vast majority of the UI; sunken is for genuinely recessed elements only, used sparingly.
surface.page color.white #ffffff

Page canvas — the dominant background color across the whole product.

surface.default color.white #ffffff

Default raised surface — cards, panels. Same value as surface.page on purpose; separated from the page by border.default, not a darker background.

surface.sunken color.gray.100 #e8e8e8

Inputs, table row stripes, code blocks — recessed relative to a default surface. Reach for this rarely; it's the exception, not the norm.

surface.dim color.gray.50 #f5f5f5

A barely-dimmed surface, one step lighter than sunken — for de-emphasized rows that must read quieter than surface.default without looking recessed like a form field (added 2026-07-24 for ThreadListItem's read inbox rows: sunken/gray.100 read as too heavy a stripe next to unread's white; explicit feedback asked for gray.25-or-50 territory). Use for read/visited/muted list rows, not as a generic nested-container background — the same restraint rule as sunken.

surface.overlay literal rgba(21, 25, 30, 0.5)

Modal/drawer backdrop scrim. The one legitimate opacity use in this system — it must composite over arbitrary page content, unlike bg.* tints which sit on a known surface.

surface.disabled color.gray.100 #e8e8e8

Disabled control background.

surface.inverse color.gray.900 #2b2b2b

The one dark surface role in an otherwise light-themed system — Tooltip's background. Pair with text.onFill/icon.onFill (white), never text.default. Added 2026-07-21 for the overlay-family components; not a general 'dark mode' token, scoped to small inverse-context UI.

bg

Passive status surfaces (banners, badges, notification chips) — solid light tints, not opacity. Pair with the matching text.* or icon.* color at the same role, never with text.default.

Added 2026-07-22 for Composer's AI Assist button — a genuine cross-product need (Message Center's composer and the future AI chat product both want a distinct 'this is the AI feature' accent), same bar surface.inverse was added under. violet was already an unused-as-semantic-role primitive family, picked over the 4 existing status roles on purpose — none of primary/success/danger/warning mean 'AI', reusing one would misattribute the feature to an unrelated status.

text

Content color. Role text (primary/success/danger/warning) sits at each family's 600 step — AA text-safe (≥4.5:1). muted is a deliberate exception, see its own note.
text.default color.gray.950 #181818

Default body/heading/title text.

text.secondary color.gray.600 #696969

Supporting text — still AA text-safe (>=4.5:1).

text.muted color.gray.500 #808080

Placeholders, captions, timestamps — intentionally below AA text contrast (~3.9:1); never use for content the user must read to complete a task.

text.disabled color.gray.300 #b4b4b4
text.onFill color.white #ffffff

Text/label sitting on a solid fill.* color (button labels, filled badges). Literal white, not a ramp step — none of the fill.* colors are dark enough to need anything else. Must be paired with semibold/bold weight: at fill's 500 step, contrast against white lands at 3.7-4.4:1 (large-text/UI-component AA, not the 4.5:1 small-text threshold) — checked directly, true for every role, not just one.

avatar

Categorical identity tints for Avatar's initials fallback — a person with no photo gets one of these 8 hues assigned deterministically (hash their name to a slot), so distinct people read as distinct colors across a list instead of every fallback avatar being the same gray. Same hue order and reasoning as tokens/primitives/chart-series.tokens.json (validated CVD-safe adjacency) but a separate token set on purpose: chart-series sits at the 500 step for saturated lines/bars on a white plot area, this sits at 100 (bg, pastel) / 600 (text, AA-safe — same step text.primary/success/danger/warning already use) for a quiet fallback badge, not a data mark. Don't reuse chart-series' own tokens here, and don't reuse these for charts.

tag

Decorative, non-semantic categorical color for generic tagging/labeling (Badge's 'color' axis, e.g. a Notion/Linear/GitHub-style label picker) — deliberately separate from the 5 meaningful status roles (bg.*/fill.* primary/success/warning/danger + this group's own gray). Picking tag.orange means 'I want an orange label', not 'this is a warning'. Two intensities per hue: tint (pale bg + colored text, same 100/600 pairing bg.*/text.* already use) and solid (saturated bg + text.onFill, same 500-step + white pairing fill.* already uses) — same contrast trade-off already accepted for fill.primary/success/danger/warning (3.7-4.4:1 large-text/UI-component AA, not 4.5:1 small-text; pair with semibold/bold label weight). 4 of the 10 hues (blue/red/green/amber) are pure aliases of the existing primary/danger/success/warning role tokens, not new colors — 'color=blue' and 'role=primary' render identically on purpose, since blue already means primary/info everywhere else in this system. gray aliases role=neutral for tint only — see gray's own $description for why solid diverges. Only orange/violet/magenta/teal/brown are genuinely new leaf references. Same hue order as chart-series/avatar for one consistent categorical rhythm across the system.
