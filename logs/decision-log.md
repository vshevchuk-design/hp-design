## 2026-07-20 (cont. 4) — semantic color tokens

- Decided to define core semantic color roles now rather than waiting for components: bg/text/icon/border/status/fill roles are universal (don't depend on which component gets built first), and the project's own stated rule ("build strictly on tokens") needs them to exist before the first component, or that component would have to hard-code primitives and get refactored later. Narrower, component-specific tokens (e.g. a chip's selected-state color) stay deferred until that component exists.
- Added `tokens/semantic/color.tokens.json` — 7 role groups (surface, bg, border, text, icon, fill, status), aliasing `tokens/primitives/color.tokens.json` via DTCG `{color.family.step}` refs, never duplicating hex. Modeled on the same bg-vs-fill split Anthropic's CDS token system uses (pale tint for passive status surfaces + text-role pairing, vs saturated solid for interactive controls + on-fill pairing) — referenced as a good pattern earlier in the project.
- Applied the primitives' own 500-vs-600 rule consistently: icon.* role colors use each family's 500 step (WCAG 3:1, graphics), text.* role colors use 600 (WCAG 4.5:1, small text) — same rule, correctly split by which one actually applies.
- Computed (not assumed) on-fill text contrast: checked white text and dark text (against the real text.primary ink, not literal black) on all four 500-step fills. Neither option reaches 4.5:1 on any of them — all land 3.7–4.8:1 regardless of choice. Conclusion: fill.* labels must be semibold/bold (relying on the WCAG large-text/UI-component 3:1 relief), documented directly on `text.onFill`, not left as a silent trap. Chose white uniformly across all four roles (more conventional, avoids an inconsistent per-role light/dark split for a marginal difference).
- `fill.success/danger/warning` alias `status.success/danger/warning` rather than duplicating the primitive ref — encodes that a fill is colored red *because* red means danger, not as a coincidence.
- `surface.overlay` is the one deliberate opacity value in the whole color system (`rgba(21,25,30,0.5)`, modal/drawer backdrop) — everything else uses solid tints per the earlier opacity-vs-tints decision, since a backdrop must composite over arbitrary page content while bg.* tints sit on a known surface.
- Added `docs/semantic-colors.html` (`tools/build-semantic-colors-doc.mjs`), resolving multi-level aliases (including alias-of-alias, e.g. fill.danger → status.danger → color.red.500) for display. First pass duplicated each group's description (a hardcoded legend string in the build script alongside the token's own `$description`) — fixed by adding `$description` to every semantic group in the token file and rendering only that, removing the hardcoded copy, so there's one source of truth for the legend text.
- User feedback: the doc page only showed resolved hex, not which primitive it aliases — the token file itself was always alias-based (`{color.gray.25}`, never raw hex), but that wasn't visible in the UI. Added an alias label to every swatch card. Also: surfaces read as "too gray" — `surface.page` was `gray.50`, one step more tinted than `surface.default` (`gray.25`), so the page canvas never actually read as the near-white the brand wants. Changed `surface.page` to `gray.25` too (same value as `surface.default`, on purpose) — cards now separate from the page via `border.default` (a hairline), not a background-color shift, matching the flat Stripe/Linear look the brief asked for. `surface.sunken` (`gray.100`) stays reserved for genuinely recessed elements only (inputs, code blocks, table stripes) — the exception, not the default.
- Bigger follow-up catch from the user: no literal white or black existed in primitives at all — black was fine (gray-950 already reads as near-black text ink), but white was a real gap. Separately, they noticed the gray ramp carried a deliberate blue tint (same hue as primary blue, low chroma) and, once surfaces leaned on gray-25 for the dominant background, that tint became visible enough to make surfaces look accidentally blue-branded.
- Fixed both: regenerated the gray ramp with chroma 0 (fully achromatic — `#fafafa`, `#f5f5f5`, `#808080`, etc, no hue at all) so neutrals never imply a brand color; added `color.white` (`#ffffff`) as its own literal primitive, explicitly not derived from the gray ramp (gray-25 is near-white but isn't identical to it). `surface.page`/`surface.default` and `text.onFill`/`icon.onFill` now alias `{color.white}` instead of `gray.25` or a hardcoded literal string — single source of truth. Added an "Absolutes" section to `docs/colors.html` so `white` is visible on the primitives page itself, not just implicitly through semantic tokens.
