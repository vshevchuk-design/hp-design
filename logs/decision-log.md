# hp-design — decision log

Running, append-only log of what happened and what was decided. No formal tiers yet (no hot-memory workspace, no separate wiki) — just a chronological record so nothing gets lost. Newest entries at the bottom.

## 2026-07-20

- Repo created empty on GitHub (`vshevchuk-design/hp-design`), cloned locally. Default local SSH key belonged to a different GitHub account (`budda-hustle`) with no access — generated a dedicated key and a `github-vshevchuk` SSH host alias so both identities coexist.
- Decided token architecture: DTCG-format JSON as the source of truth (`tokens/primitives/`), stack-agnostic — will transform to CSS vars / Tailwind / etc. per consumer later. Layering: primitives → semantic (not started) → components (not started).
- Generated color primitives programmatically in OKLCH instead of hand-picking hex, anchored to the existing Figma brand colors (primary blue `#1565C0` etc.) but with consistent hue/chroma across each ramp — the reason the old brand's darkened yellow read as "muddy" was chroma collapsing at low lightness; keeping chroma consistent avoids that.
- Result: `tokens/primitives/color.tokens.json` — 10 ramps (gray + blue, red, green, amber, orange, violet, magenta, teal, brown), steps 25→950. Rule baked in: **step 500 = brand/UI-safe (≥3:1 contrast)**, **step 600 = AA text-safe (≥4.5:1 contrast)**.
- `tokens/primitives/chart-series.tokens.json` — validated categorical/chart palette (8 hues, fixed order: blue, green, magenta, amber, teal, orange, violet, red), passed the `dataviz` skill's six-checks CVD-safety validator (worst adjacent CVD ΔE 8.3, normal-vision floor 20.7, all ≥3:1 on `#fcfcfb`).
- Decided: background/notification tints use solid light steps (e.g. `blue-100`), not opacity overlays — opacity was the root cause of the original Figma sub-colors clashing across different surfaces.
- Built `docs/` as a small storybook-style static site: `index.html` (overview + left nav) and `colors.html` (palette page). `tools/build-colors-doc.mjs` regenerates `colors.html` from the token JSON — never hand-edit hex in the generated doc.
- **Open / deferred:** color review feedback — blue reads too fresh/saturated, yellow and orange read too dark, violet too light. Decided to move forward with current values and revisit once real UI mockups exist, not tune blind now.
- Discussed a long-term "AI Design Operating System" workflow (staged pipeline, tiered memory, review sandbox, decision log, archive) as a north-star direction. Decision: adopt pieces lazily, only when a real repeated pain shows up — not build the full pipeline/command set upfront. This log is the first small piece of that (the "Log & Learn" step), deliberately without the hot-memory/wiki tiers yet.
- Hosting plan: deploy `docs/` on Vercel via GitHub auto-deploy. Not yet connected — needs the user to link the GitHub repo to a Vercel account themselves.
- Status at end of session: nothing committed to git yet — all files exist locally only.

## 2026-07-20 (cont.)

- Added `tokens/primitives/dimension.tokens.json`, `radius.tokens.json`, `z-index.tokens.json` from the user's existing Figma scales. Dimensions matched Tailwind's spacing scale value-for-value (linear 4px grid) — kept as-is. Renamed the sentinel `dim-100` (999px, breaks the N*4 formula) to `dim-max` to match how radius already referenced it.
- Reviewed the z-index scale's ordering: initially flagged the "floating on page" tier (dropdown/popover/tooltip, 100-120) as a bug for sitting below Drawer/Modal tiers. User's counter-example (a page-level dropdown must not visually leak through a modal opened afterward) showed that a single globally-promoted floating tier would trade one bug for a worse one. Re-read the original design: it already has the right shape — `z-drawer-floating` / `z-modal-floating` / `z-modal-floating-2` exist precisely so a Select/Popover/Tooltip picks the slot matching whatever context (page / drawer / modal-1 / modal-2) it's currently mounted inside, rather than carrying one fixed z-index. Kept all values exactly as designed; documented the usage contract in each token's `$description` instead of renumbering anything.
- Open follow-up (component layer, not tokens): the context-aware z-index selection needs an actual mechanism when Select/Popover/Tooltip get built — e.g. a React context each Drawer/Modal provides to descendants so they know which "-floating" token to use. Not needed until those components exist.

## 2026-07-20 (cont. 2) — typography

- Added `tokens/primitives/typography.tokens.json` (family/weight/size/leading/tracking) and `text-styles.tokens.json` (17 composite DTCG `typography` styles) from the user's Figma spec. Font: Sora — confirmed English-only product, so Sora's lack of a Cyrillic subset on Google Fonts (checked directly against the API) is not a blocker.
- Size scale matches Tailwind's font-size scale value-for-value; `base` is deliberately 14px (not Tailwind/browser's 16px convention) — an app-density choice, same pattern as Linear/Stripe Dashboard/Notion, not an error.
- Two fixes applied vs. the literal Figma spec, both confirmed with the user first: `body-lg` was labeled with size `md` (16px) in the spec table, duplicating `body-md` and breaking the naming pattern every other row follows (`heading-lg`→`lg`, etc.) — fixed to `lg` (18px). `title-xl/2xl/3xl` used `leading-normal` (140%) like everything else, but at 20–30px bold that reads as too much air for a single-line title — switched those three to the already-existing `leading-tight` (120%), matching how Stripe/Linear/Vercel tighten leading as size grows.
- Added `tracking-wide` (0.04em, new — nothing in the source defined a non-zero tracking) and applied it to `label-sm`/`label-base`, which are all-caps and were at 0 tracking — all-caps at zero tracking reads cramped, near-universal fix.
- Downloaded Sora as 3 static woff2 weights (400/600/700, not the variable font — matches the 3-weight token scale exactly) into `assets/fonts/sora/`, plus a `sora.css` with `@font-face` rules.
- Extended the docs storybook: `docs/typography.html` (generated by `tools/build-typography-doc.mjs`, same pattern as colors), nav updated on all three pages so Typography is a real link, not "soon".

## 2026-07-20 (cont. 3) — layout page + docs legends

- Added `docs/layout.html` (dimensions + radius + z-index, generated by `tools/build-layout-doc.mjs`) and a "Legend/usage" section on every token docs page (colors, typography, layout) explaining where each token is meant to be used, not just its raw value — standing rule going forward, saved to memory.
- Fixed a real ordering bug: `Object.entries()`/JSON always sorts integer-like string keys ("0","1",…"96") numerically ahead of non-integer-like keys ("0_5","max"), regardless of insertion order — this is baked into the raw `dimension.tokens.json` file itself, not just the doc rendering. Fixed by sorting the doc table explicitly by resolved px value rather than trusting object key order; left the source JSON as-is since key order there is not semantically meaningful (DTCG consumers look up by name, not position).
- Corrected the dimensions legend after user feedback: 8px (`dim-2`) is not a "tight/border" value, it's the single most-used base gap in the whole scale (default spacing between cards, buttons, form fields) — recalibrated all the bucket boundaries around that.
- Z-index context column was wrapping to multiple lines — added short one-line context summaries (kept the fuller reasoning in the token JSON's own `$description`) plus an `overflow-x: auto` wrapper as a safety net.
- Radius preview boxes were too small (28px) to show the difference between md/lg/xl/full, which all looked like full circles — enlarged to 72px and removed the artificial px clamp, letting CSS's own border-radius clamping do the work authentically.

## 2026-07-20 (cont. 4) — semantic color tokens

- Decided to define core semantic color roles now rather than waiting for components: bg/text/icon/border/status/fill roles are universal (don't depend on which component gets built first), and the project's own stated rule ("build strictly on tokens") needs them to exist before the first component, or that component would have to hard-code primitives and get refactored later. Narrower, component-specific tokens (e.g. a chip's selected-state color) stay deferred until that component exists.
- Added `tokens/semantic/color.tokens.json` — 7 role groups (surface, bg, border, text, icon, fill, status), aliasing `tokens/primitives/color.tokens.json` via DTCG `{color.family.step}` refs, never duplicating hex. Modeled on the same bg-vs-fill split Anthropic's CDS token system uses (pale tint for passive status surfaces + text-role pairing, vs saturated solid for interactive controls + on-fill pairing) — referenced as a good pattern earlier in the project.
- Applied the primitives' own 500-vs-600 rule consistently: icon.* role colors use each family's 500 step (WCAG 3:1, graphics), text.* role colors use 600 (WCAG 4.5:1, small text) — same rule, correctly split by which one actually applies.
- Computed (not assumed) on-fill text contrast: checked white text and dark text (against the real text.primary ink, not literal black) on all four 500-step fills. Neither option reaches 4.5:1 on any of them — all land 3.7–4.8:1 regardless of choice. Conclusion: fill.* labels must be semibold/bold (relying on the WCAG large-text/UI-component 3:1 relief), documented directly on `text.onFill`, not left as a silent trap. Chose white uniformly across all four roles (more conventional, avoids an inconsistent per-role light/dark split for a marginal difference).
- `fill.success/danger/warning` alias `status.success/danger/warning` rather than duplicating the primitive ref — encodes that a fill is colored red *because* red means danger, not as a coincidence.
- `surface.overlay` is the one deliberate opacity value in the whole color system (`rgba(21,25,30,0.5)`, modal/drawer backdrop) — everything else uses solid tints per the earlier opacity-vs-tints decision, since a backdrop must composite over arbitrary page content while bg.* tints sit on a known surface.
- Added `docs/semantic-colors.html` (`tools/build-semantic-colors-doc.mjs`), resolving multi-level aliases (including alias-of-alias, e.g. fill.danger → status.danger → color.red.500) for display. First pass duplicated each group's description (a hardcoded legend string in the build script alongside the token's own `$description`) — fixed by adding `$description` to every semantic group in the token file and rendering only that, removing the hardcoded copy, so there's one source of truth for the legend text.
- User feedback: the doc page only showed resolved hex, not which primitive it aliases — the token file itself was always alias-based (`{color.gray.25}`, never raw hex), but that wasn't visible in the UI. Added an alias label to every swatch card. Also: surfaces read as "too gray" — `surface.page` was `gray.50`, one step more tinted than `surface.default` (`gray.25`), so the page canvas never actually read as the near-white the brand wants. Changed `surface.page` to `gray.25` too (same value as `surface.default`, on purpose) — cards now separate from the page via `border.default` (a hairline), not a background-color shift, matching the flat Stripe/Linear look the brief asked for. `surface.sunken` (`gray.100`) stays reserved for genuinely recessed elements only (inputs, code blocks, table stripes) — the exception, not the default.
- Bigger follow-up catch from the user: no literal white or black existed in primitives at all — black was fine (gray-950 already reads as near-black text ink), but white was a real gap. Separately, they noticed the gray ramp carried a deliberate blue tint (same hue as primary blue, low chroma) and, once surfaces leaned on gray-25 for the dominant background, that tint became visible enough to make surfaces look accidentally blue-branded.
- Fixed both: regenerated the gray ramp with chroma 0 (fully achromatic — `#fafafa`, `#f5f5f5`, `#808080`, etc, no hue at all) so neutrals never imply a brand color; added `color.white` (`#ffffff`) as its own literal primitive, explicitly not derived from the gray ramp (gray-25 is near-white but isn't identical to it). `surface.page`/`surface.default` and `text.onFill`/`icon.onFill` now alias `{color.white}` instead of `gray.25` or a hardcoded literal string — single source of truth. Added an "Absolutes" section to `docs/colors.html` so `white` is visible on the primitives page itself, not just implicitly through semantic tokens.

## 2026-07-20 (cont. 5) — icons

- User shared a screenshot inventory of icons already used across the current product (grouped: Navigation, Action, Status, Map, Content, Hardware, Audio & video, Communication), with a mix of exact and approximate/friendly names, and asked to pull the matching icons from google/material-design-icons — Filled style, SVG (not the font), downloaded rather than linked live from Google.
- The classic repo is enormous (multiple styles × PNG densities × font files); pulling `src` alone is still large, so instead fetched the repo's git tree via the GitHub API scoped to the `src` subtree (not the whole-repo recursive tree, which truncates before reaching `src`), giving the full list of ~2170 available "Filled" 24px icon names without downloading anything yet.
- Fuzzy-matched the user's ~110 requested labels against that real name list (exact match first, `difflib` close-match fallback, manual resolution for ambiguous ones) rather than guessing slugs from memory — caught real mismatches this way (e.g. "favorite_outline" → actual name is `favorite_border`; "download" arrow-into-tray → `get_app`; "Right"/"Left" turn arrows → `turn_right`/`turn_left`).
- A handful of requested items aren't extractable from Material Icons at all and were dropped rather than force-mapped: Grade A/B/C/F letter badges, plain color swatches ("Rect_green"/"Rect_purple"), a "primary" badge, and the "Class location" pin+graduation-cap icon — all clearly custom/product-specific glyphs, not from any icon set. Flagged for separate custom design work later.
- Added 27 additional common UI icons not in the user's list but expected to be needed soon (check, star/star_border, content_copy, refresh, cloud_upload, share, logout/login, sort, grid_view/view_list, dark_mode/light_mode, error_outline, check_circle, add_circle, remove, calendar_today, schedule, mail, visibility_off, delete/delete_outline, chevron_left/right, expand_more/less) — all verified to exist in the real name list before adding.
- Downloaded 136 SVGs total to `assets/icons/material-filled/{slug}.svg` (parallel curl, `raw.githubusercontent.com` — no GitHub API rate limit hit since only one API call was needed for the tree listing). Post-processed every file to add `fill="currentColor"` on the root `<svg>` (the source files ship with no fill on the glyph path, defaulting to black) so icons inherit ink color and work in both light/dark mode.
- Added `docs/icons.html` (`tools/build-icons-doc.mjs`) — icons embedded as inline SVG (required for `currentColor` to work; an `<img src>` reference would opt out of CSS color inheritance), grouped into the same categories as the user's source inventory, with a client-side name search/filter. Per the token-docs-legend standing rule, every icon shows a "not yet used" placeholder tag — to be rewritten to real component references as consumers appear, not before.

Re-run the same tree-fetch + fuzzy-match approach next time more icons are needed rather than re-guessing slugs from memory.
