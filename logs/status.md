## Designs layer (prototype explorer) — added 2026-07-24

The sidebar on every docs page now has **DS / Designs tabs** (top of nav). DS = the design system (everything below). Designs = a prototype explorer: an accordion per product → interactive prototype pages under `docs/designs/`. All of it lives in `tools/lib/nav.mjs` (`DESIGN_PRODUCTS` + tab styles/script emitted inline by `renderNav`, so it stays a one-file change; `renderNav` takes `{ basePath }` for pages one directory deeper). **`docs/index.html` has no generator — its sidebar block was hand-updated and must be kept in sync by hand**, same trap as its Sora font link. That hand-copied block includes **the whole inlined logo SVG**, so an edit to `assets/highpoint-logo.svg` needs the same edit applied to `docs/index.html` by hand (every other page picks it up from `renderNav` on rebuild). Bit us once already: the 2026-09-07 wordmark alignment fix had to be applied twice.

**Every designs page's chrome is now one shared module — `tools/lib/design-viewer.mjs` (extracted 2026-09-07).** `renderDesignViewer({ activeKey, title, heading, sub, versions })` returns the whole viewer page: docs chrome + the device bar (Mobile/Tablet/Desktop segmented Tabs · a **Versions** dropdown · Open standalone) + the iframe frame. It used to be duplicated byte-for-byte in both Message Center builders (the drift risk this file had accepted for v1); a designs page is now a ~15-line call, same one-file-change reasoning as `nav.mjs` — **put any new cross-page viewer control here, never in a builder**. The extraction is behaviour-neutral: both app files came out byte-identical.
- **Versions are real snapshots, not labels**: `versions` is a newest-first list of `{ label, note?, file }` (file relative to `docs/designs/`); `[0]` is what loads, and picking one swaps both the iframe `src` and the Open-standalone href. Every page currently has exactly one entry, `v1 · current`, pointing at its live app file — no fake history was back-filled. **Convention for the next one: before starting a big rework, copy the current app to `docs/designs/versions/<slug>-vN.html` and add an entry**, so the previous design stays comparable side by side.
- The control is **Select's closed trigger + Listbox's single-select popover** (both resolved from their own token files — the same composition the prototypes use internally). Single value line, no floating label: Select's label+value stack needs lg (48px) and would stand taller than the 40px device tabs beside it, so "Version" is a chrome-level label in the bar. Native `popover` + a `toggle` listener that anchors it under the trigger; **that event is queued async, so don't read `aria-expanded`/geometry in the same tick as `.click()`** when testing by hand.
- Verify designs pages with the HTTP server rooted at the **repo root**, not `docs/` — `../../assets/fonts/sora/sora.css` only resolves from the root (serving `docs/` as root 404s it silently and brings back the italic-Sora symptom).

**The portal's app shell is one module — `tools/lib/app-shell.mjs` (extracted 2026-09-07 with the second portal screen).** It owns the page frame, the 64px topbar (declared `dim.16`, hairline inside), the wordmark with nav.mjs's `#090D19` → `currentColor` swap, and Button secondary's recipe (base icon-only + sm), plus a `SHELL_COLOR_PATHS` list to merge into a page's own `colorPaths`. Extracted *before* writing the second screen rather than after: the two MC builders already duplicate their shell between them (a v1 drift risk this file has carried for months) and the viewer chrome had the same problem until `design-viewer.mjs`, so a third copy was not going to happen. Springboard was migrated onto it — verified by set-comparing the generated CSS rules and the `--tok-*` map before/after: **only the three shell class names changed (`sb`/`sb__topbar`/`sb__logo` → `app`/`app__topbar`/`app__logo`), all 36 vars identical, every other rule identical.**

## Brand ramp (2026-10-19) — one institution colour → a 13-step primary palette

`exports/brand-ramp.js` (the developer handoff file and the single source; `tools/lib/brand-ramp.mjs` re-exports it + its source text for inline pages). Clients can change the primary colour; this generates the whole ramp from one hex. **Finding it rests on: every ramp in the palette shares the same OKLCH lightness per step** (25 .985 · 50 .970 · 100 .930 · 150 .895 · 200 .860 · 300 .770 · 400 .680 · 500 .600 · 600 .520 · 700 .440 · 800 .360 · 900 .290 · 950 .212), hue is constant along a ramp, and chroma follows one profile relative to the 500 step (median of blue/red/violet/orange/magenta: .039 .076 .180 .255 .370 .665 .999 1 .997 .873 .722 .584 .428). Algorithm: (1) **anchor** = the step nearest the input's lightness (user's framing: "find which step it's closest to, then build the rest"); the input takes that step **exactly**; (2) the other steps = fixed L, input hue, peak chroma = input C ÷ profile at its L, × profile, clamped to sRGB (×0.98). Also returns `brand.onText` (white or #121921, by contrast) and contrast checks. **Verified**: hp-design's own blue/red 500 regenerate their ramps within 1–3 units per channel (violet's hand-tuned darks differ). Proposed (not decided): semantic roles stay on fixed steps (fill.primary = 500 …) so contrast is school-independent; the exact brand colour goes on brand surfaces (sidebar). **Open finding: white text on step 500 is ~3.8–4.4:1 for every hue, our own blue.500 included (4.0) — under AA 4.5 for 14px button labels**; a system-wide question (buttons on 600?), not a brand-ramp one. A "Brand color" docs page (pick a colour → ramp, anchor, checks, mini UI preview) was offered, not built.

## Locked-in conventions (don't relitigate these without reason)

- **`surface.page` is `gray.25`, not white** (changed 2026-09-07 on request). The app shell's backdrop is a near-white cool neutral; every surface sitting on it stays `surface.default` (white). That is deliberately ONE tint level — not the layered-grays habit the conventions warn about — and it does not replace the border: cards still carry their `border.default` hairline, the page tint just stops white-on-white from depending on the hairline alone. Note this reverses a same-day instruction to make the Springboard page white; the page had been on `surface.dim` (gray.50) then, which read as a properly gray page — gray.25 is the middle ground that request was actually after.
- **A blue-border hover always carries a pale blue fill too — `bg.primaryHover` (blue.50)** (added 2026-09-07 on request: "у елементів де по ховеру тіки обводка синя… додати легку синю заливку"). The blue interactive states now escalate in three steps instead of two: **rest (no tint) → hover `bg.primaryHover` blue.50 + `fill.primary` border → pressed/selected `bg.primary` blue.100**. Applied to all four components whose hover had been border-only — Card's interactive variant (and therefore the Springboard tiles), Chip toggle unchecked, Checkbox, Radio — from that one role, so they can't drift. Each one is scoped to the *unchecked/unpressed* case; a checked control keeps its solid `fill.primary*` fill.
- **EVERYTHING RENDERS ON THE 4px GRID — check the output, not just the tokens.** The `dim.*` scale is already a 4px grid (dim.1 = 4 … dim.16 = 64, plus 2px half-steps), so the *inputs* are nearly always fine; what breaks is the *sum*. A topbar built as `dim.3 padding + 40px control + dim.3 padding + 1px border` renders at **65px** — every token on-grid, the result off it. **So for any bordered band (topbars, headers, footers), declare the height (`height: dim.16`) and let the hairline sit inside it via border-box, with `padding: 0 <horizontal>`** — never sum vertical padding plus a border. Verify with `getBoundingClientRect().height % 4 === 0`, because that 65px passed a CSS read-through. Off-grid is fine only where already documented as deliberate: 1px/0.5px hairlines, the designs viewer's +2px iframe-border compensation, and half-steps used as small gaps.
- **App shells share one topbar height: exactly 64px (`dim.16`), border included.** Springboard was 57 (dim.2) and the Message Center 73 (dim.4 at wide); the midpoint that also lands ÷4 wins. Content band ends up 63px with the 40px control optically centred (12 above / 13 below). If a new app shell gets a topbar, declare `dim.16`.
- **Every ramp has 13 steps: 25 / 50 / 100 / **150** / 200 / 300 … 950** (150 added 2026-09-07). 100→200 was the ramp's harshest jump because the lightness deltas accelerate across the light end (.015, .04, .07); 150 sits at L 0.895 and splits the biggest one into two .035s. Its chroma is the **geometric** mean of its neighbours, not the arithmetic one — chroma roughly doubles per light step, so an arithmetic midpoint reads closer to 200 than to 100. It's an interpolation step, not a new default: reach for it only when a tint genuinely needs to sit between the two.
- **The light-end chroma profile is a measurable palette rule, not taste.** The five well-behaved ramps (blue/red/orange/violet/magenta) all place their light steps at the same fraction of their OWN 300-step chroma: **25 = 0.057×, 50 = 0.113×, 100 = 0.264×, 200 = 0.557×** (median). green and teal were at ~2.7–3× that, which is why `teal.100` was `#88fffe` (near-pure cyan) beside pale siblings like `blue.100` — retuned to the profile 2026-09-07. Check a new or edited ramp against this profile before shipping it. **Known remaining anomaly (offered to the user, not yet changed):** teal and green are the only ramps whose chroma *peaks at 300* rather than 500 (teal C300/C500 = 1.28, green = 1.03, family median ≈ 0.67), which is why their 200→300 transition still reads as the steepest in the palette.
- **Brown is a warm-neutral-to-brown family, hue 58, chroma ≈ 70% of a normal ramp** (rebuilt 2026-09-07 because brown and orange were indistinguishable). Two things had to change together and the reason is structural: brown sits in the **26° corridor between orange (42) and amber (68)**, so no brown hue can be more than ~13° from one of them, while the palette's own comfortable gap is 18–22° — hue alone can't separate it. And chroma alone can't either, because at the pale end a low-chroma orange and a low-chroma brown are both just off-white (tried first, failed, verified side by side). With both moved, its light steps read as warm greige (`#f1e5dd` at 100 vs orange's peach `#ffe1d5`) and 300–500 as muted tan rather than terracotta; amber stays clear by carrying ~2.5× the chroma at every light step. Don't "fix" brown by pushing its hue further — that just collides with amber.
- **The gray ramp is a COOL neutral, not achromatic (changed 2026-09-07, explicit user call — reverses the original decision).** `color.gray.*` now carries the brand blue's own hue (254) at a small fraction of its chroma — an arc peaking at **0.030** mid-ramp and tapering to **0.002** at the pale end (pulled back the same day from a first pass that peaked at 0.040 and read "занадто сині"; the pale steps are what carry the tint on a screen full of surfaces, so they got halved hardest) — because at chroma 0 the neutrals read "прям сірий сірий", dead gray in product surfaces. **Lightness was not touched at any step**, which is why the whole contrast table moved by at most 0.06 and every documented guarantee still holds; `tools/gen-color-ramps.mjs` asserts 500 ≥ 3:1 and 600 ≥ 4.5:1 on white and refuses to write otherwise. Regenerate the ramp with that script, never by hand — and note the same script must NOT be re-run blindly over the saturated ramps (its converter differs from the original generator by ±1 unit on high-chroma steps at the sRGB gamut edge; see `tools/lib/oklch.mjs`, which also documents how the missing OKLCH generator and the unrecorded "ink" contrast reference were reconstructed). The old achromatic rationale ("so surfaces never read as accidentally brand-colored") is superseded: at this chroma the tint reads as temperature, not as brand colour.
- **The docs chrome is NOT tokenized and is still a WARM gray** (`--bg-page: #f7f7f5`, `--border: #e4e3df`, hand-written in every `build-*-doc.mjs` head template + `docs/index.html`). Since the token grays went cool, chrome and content are now two different neutral temperatures on the same page. Left alone deliberately — it's docs furniture, not product surface — but if it ever gets aligned, it's a 46-file chrome edit, not a token change.
- **`border.default` is `gray.150`** (moved off gray.200 on 2026-09-07 — "шось трохи темний"): at 200 the hairline read as a drawn line, especially once the page went to gray.25. This is step 150's first real consumer, which is why it was added. **`border.strong` stays gray.300**, so a form field's hover now moves two steps instead of one and reads more clearly. The role-coloured borders (`border.primary/success/danger/warning`) stay at their 200 tints — an error outline shouldn't get quieter.
- **A field's hover changes its FILL, not just its border — `surface.dimHover` (gray.100), and never blue.** Added 2026-09-07: hover had been `border.default → border.strong` only, which reads as almost nothing. **Blue is reserved for focus/active in this system**, so a blue hover on a field would claim a state it isn't in — the user's own framing ("синій означає активний стан"). Applies to Input / Select / Search / DatePicker trigger / Composer field / the compose dialog's fields. `surface.dimHover` is the same value as `surface.sunken` but a separate role on purpose: sunken says what a surface *is*, dimHover says what a transition *does*.
- **Fill+border on form fields** (Input/Select/Search/Composer field, + Attachment rows): **`surface.dim`** bg (gray.50 — retinted from `surface.sunken` 2026-08-03, explicit user call after seeing both in the compose prototype: "світліші поля набагато краще") + `border.default` hairline, strengthening to `border.strong` on hover, `border.focus` (blue) on focus. Not a pure outline or pure fill. Changed at the TOKEN level (input/select/search `state.default.bg`, composer `field.bg`, attachment `bg`) **and** in every builder that had the old role hardcoded in its field recipe (input/select/search/composer/attachment/message/listbox-search/pagination-select + the prototype app — `cv("surface.sunken")` → `cv("surface.dim")`, `surface.dim` added to each page's colorPaths). Disabled fields keep `surface.disabled` (gray.100), which now reads one step darker than the default field — a real visible disabled state where before the two were identical. Segmented-tabs track / kbd scaffolding stay on `surface.sunken`.
- **Neutral hover comes in TWO tiers, picked by what the control rests on (split 2026-09-07).** One token used to serve both and it was a full step too dark for the common case — a hovered table row read as a solid band, not a hover cue.
  - **Wash tier — `fill.neutralHover` (gray.100) → `fill.neutralActive` (gray.200)**: for a control whose resting surface is transparent or white. Button ghost, Pagination page-items, Tabs underline, Menu/Listbox options, DatePicker days, table + thread rows, and every small icon-button (Popover/Drawer/Modal/Chip close, Composer, Attachment).
  - **Strong tier — `fill.neutralHoverStrong` (gray.200) → `fill.neutralActiveStrong` (gray.300)**: for a neutral control that ALREADY rests on gray.100, where the wash would be invisible. Exactly three consumers: **Button secondary** (rest = `fill.neutral`), **Tabs segmented** (track = `surface.sunken`), and **Counter `onNeutral`'s inactive chip** (must stay legible against its gray.100 parent).
  - Adding a consumer: ask what colour is under it at rest. White/transparent → wash. gray.100 → strong.
  - **The split shipped broken in the prototypes and 4 overlay doc pages** and the user found it by hand ("у цих табів немає нормальних ховерів… втф???"): those files *hardcoded* `cv("fill.neutralHover")` for controls resting on gray.100 (secondary buttons, the segmented track, `.ov-btn--secondary`), so retargeting the wash made their hover identical to their resting fill. Fixed by reading the role off the component's token file — and `check-states.mjs` now fails the build on any hover that paints the resting colour. Third time the "resolve, never retype a role name" rule has caught a real bug.
- **Disabled usually keeps the same background as default**, only text/icon fade to `*.disabled` — because `fill.disabled` / `surface.disabled` / `fill.neutral` / `surface.sunken` are all literally `{color.gray.100}`. Confirmed intentional, not a bug, recurred across Button secondary, Input, Select, Search.
- **Run all three checkers after every rebuild** — `node tools/check-css-vars.mjs && node tools/check-grid.mjs && node tools/check-states.mjs`. Each one exists because a specific class of bug shipped past a passing build and was caught by eye:
  - **`check-css-vars.mjs`** — fails if a page references a `--tok-*` it never defines. Each builder emits only the vars in its own `colorPaths`, while the *values* come from component token files, so repointing a component token at a new semantic role silently yields an undefined var: no build error, no console warning, the element just loses its background. Its first run caught the live case (secondary → the new Strong tier) **plus two latent bugs nobody had noticed**: `chip.html`'s Counter `onPrimary` inactive chip had no background at all, and a caption on `badge.html` had no colour. A used name ending in `-` is treated as a runtime-concatenated prefix (prototype JS does `'var(--tok-avatar-' + hue + '-bg)'`) and only its family is asserted.
  - **`check-grid.mjs`** — fails on a declared size that isn't on the 4px grid. Scoped to `docs/designs/*-app.html`, because the un-tokenized docs chrome would bury real findings ~450 to 4. Can't add up a box (that needs layout), so the browser check stays part of the grid convention.
  - **`check-states.mjs`** — fails when a `:hover`/`:active` background resolves to the **same colour as the element's resting background**, i.e. an interaction that renders as nothing. Compares resolved `--tok-*` values, not token names, since the whole failure mode is two different roles aliasing one hex. `:disabled` states are excluded — an inert disabled control is correct, not a dead state.
- **CSS custom properties**: every resolved color is `--tok-<dotted-path-kebab>` (e.g. `fill.primaryHover` → `--tok-fill-primary-hover`), generated by `tools/lib/css-vars.mjs`. The `--tok-` prefix is load-bearing — without it a token can collide with the docs chrome's own `--text-primary`/`--border`/`--accent` (happened once, turned page text blue).
- **BEM**: shared block class (`.btn`, `.input`, `.select`, `.search`, `.tab`, `.counter`, `.page-item`, `.separator`) + `--modifier` for size/variant/state + `__element` for icon/label sub-parts. Where two variants share 100% identical sizing (Button primary/secondary/ghost; Tabs segmented/underline), the size grid is asserted identical at build time (`primarySizes.forEach(...) throw if diverged`) rather than trusted blindly — DTCG can't alias a whole sub-tree so the JSON duplicates the values, the assertion is the safety net.
- **Reused sub-components must resolve real values, never retype color-role names by hand** — caught two real bugs (Tabs' counter, both the wrong token guessed and a missing icon-disabled override) exactly from skipping this. **The rule applies to a component's own page too**: `build-button-doc.mjs` had its variant→role map hardcoded (`fillHover: "fill.neutralHover"`), so when `button.tokens.json` moved secondary's hover to the Strong tier the page would have kept painting the old role — a hover identical to its own resting fill, with no error. It now reads every role off the token file and asserts each one is in `colorPaths`.
- **No hard caps on repeating collections** (Pagination pages, Tabs count) — `overflow-x: auto` + a practical guideline in the legend, confirmed with the user as the preferred approach over a hard-coded limit.
- Every docs page prints the *exact* generated CSS string both live and as the "copy this" code sample — one source, can't drift. Icons in printed code samples are `<!-- icon: name --></svg>` placeholder comments, not full path data.
- Radius is `radius.default` (8px) everywhere unless there's a specific reason otherwise (e.g. Tabs' `radius.md` track with a deliberately nested `radius.default` pill). **Concentric-radius rule for when a rounded shape sits flush inside another rounded shape** (touching edges, like Tabs' pill inside its track): `inner radius = outer radius − padding between them`, or equivalently `outer = inner + padding` — otherwise the two curves don't share a center and the gap looks uneven/bulging even with identical padding on all sides. Only relevant when one rounded shape is actually nested directly inside another (researched 2026-07-22) — a plain Card sitting on the page isn't nested in anything rounded, so it just uses `radius.default` with no extra math. Will matter for Modal/Drawer panel-inside-overlay later.
- **No implicit "default" padding value on Box** — confirmed against Chakra/MUI's own Box (2026-07-22 research): neither gives Box an implicit padding, always an explicit token choice, because unlike Button's height (one genuinely privileged size, used ~90% of the time) there's no single "right" padding for a generic container — it's entirely contextual (a chip vs. a section). Box's `none/xs/sm/md/lg` padding steps stay equally-weighted on purpose, no step singled out as "the" default. (Card, being one fixed *opinionated* composition rather than a generic primitive, is correctly the one that does have one fixed padding — `dim.4`.)
- **Native `<input>` for Checkbox/Radio**, visually hidden (clip-rect technique, not `display:none`) — keyboard/forms/screen readers/`:indeterminate` all work for free, only the paired `<span>` box/circle is repainted via `~` sibling selectors off `:checked`/`:disabled`/`:focus-visible` on the real input. Checkmark/dash glyphs reuse the shared Material icon set (`check.svg`/`remove.svg`), not bespoke assets.
- **`border.primary`/`border.success`/`border.danger`/`border.warning` are pale 200-tint roles, not brand-strength** — `border.primary` (blue.200, `#b2d4fe`) is much lighter than `fill.primary` (blue.500, `#077fec`). Radio's checked state first used `border.primary` for the ring, pairing a washed-out ring with a saturated dot — looked broken, caught before shipping. Fixed to reuse `fill.primary` for both ring and dot (same pattern Checkbox's checked state already uses for bg+border). `border.danger` at Input/Select error *is* the pale tint used correctly (a hairline-weight error border, not an emphasis border) — don't assume every `border.*` role is interchangeable with its same-named `fill.*`/`icon.*` counterpart; check the resolved hex before reusing one for emphasis.
- **No shadow/elevation token family exists anywhere in this system** — every surface (Input/Select/Search fields, now Card) draws separation with a `border.default` hairline, never a drop shadow, matching the flat Linear/Stripe-Dashboard/Notion aesthetic `typography.tokens.json`'s own `$description` names as the explicit reference. Card was built border-only on purpose, not because shadow was forgotten — don't introduce a shadow primitive for one component without a real cross-component need (e.g. a floating/overlay component that genuinely needs to look "lifted" off the page, unlike a page-level content Card).
- **Prefer white/default surface + hairline borders over stacking multiple gray tint layers for hierarchy** (e.g. gray page → grayer card → white inner card). User's prior design habit was layered depth via progressively darker/lighter grays (sometimes 3 levels); explicit call **2026-07-22**: favor a cleaner look for this system, closer to Linear/Stripe/Notion, and lean on `border.default` (or spacing/radius) to separate sections *before* reaching for a second surface tint. `surface.sunken` stays reserved for genuinely recessed elements (Input/Select/Search fields) — don't reach for it as a general "nested container" background. This is a default lean, not an absolute ban: a deliberate gray-card-on-gray-page case is still fine when a screen genuinely needs that grouping — just shouldn't be the reflex choice for every new panel/section.
- **Always render every state-dependent glyph/element in the markup, hidden via CSS, rather than conditionally injecting it at build time** — Checkbox's check/indeterminate icons were first only inserted into the HTML when the *doc-build script* had that item pre-checked; any live checkbox a user actually clicked (e.g. in the CheckboxGroup demo) had no icon element in the DOM at all, so clicking it just turned the box solid blue with no tick inside. Fixed by always emitting both glyphs with `display:none`, shown only via `:checked`/`:indeterminate` on the real sibling input — the same "let the real cascade drive it" principle already used for background/border color. Check any future component with build-time-conditional markup for the same trap.
- **`border.focus` is `{color.blue.600}` (not 500), ring width is `{dim.1}` = 4px (not `dim.0_5`/2px) — system-wide, affects every component with a focus ring/border** (Button, Input, Select, Search, Checkbox, Radio, Tabs, Card). Changed **2026-07-22** while designing Card's interactive hover/pressed: once hover/pressed started using `fill.primary` (blue.500) for a stronger, more visible cue, focus needed to move up a step too so keyboard focus stays unambiguously the *strongest* state — mouse hover is the common case but focus is the accessibility-critical one (a keyboard/switch user has no other way to see where they are), so it must out-rank hover, not just differ from it. Don't reset this back to 500/2px without re-checking every component's ring, not just Card's.
- **Unchecked-hover on Checkbox/Radio is also `fill.primary` now, not `border.strong`** — same "gray reads as too weak a cue" lesson from Card, applied consistently (2026-07-22). And for the checked+hover combination specifically, reuse `fill.primary`→`fill.primaryHover` (blue.500→600) — the *exact same pair* Button primary already uses for its own fill→hover darkening — rather than inventing a new darkening step. General pattern worth remembering: when a control's "on"/filled state needs a hover-darken, check whether the semantic layer already has a `*Hover` sibling for that fill role before creating anything new (it usually does — `fill.primaryHover`/`successHover`/`dangerHover`/`warningHover`/`neutralHover` all already exist).
- **Shadow/elevation tokens: introduced 2026-07-22** (`tokens/primitives/shadow.tokens.json`, 3 steps: sm/md/lg), exactly when the overlay family got built, per the plan flagged earlier — scoped deliberately to Tooltip/Popover/Drawer/Modal only. Every other surface (Input/Select/Search fields, Card) still draws separation with `border.default`, never a shadow — don't reach for `shadow.*` outside the floating-UI family without a genuinely new floating component to justify it.
- **Overlay components use native browser mechanisms, not hand-rolled JS state** — Tooltip is pure CSS (`:hover`/`:focus-within`); Popover uses the native `popover`/`popovertarget`/`popovertargetaction` HTML attributes (Popover API); Drawer/Modal use `<dialog>`+`showModal()`. All four get focus-trap/Escape/outside-click/top-layer stacking for free from the browser — zero JS for state management, only a small positioning script for Popover and a one-line `showModal()` call for Drawer/Modal (dialogs have no declarative "open" attribute the way Popover has `popovertarget`). Close buttons use `<form method="dialog">`, not `onclick` handlers. Follow this same native-first approach for any future overlay-ish component (e.g. Select's dropdown) before reaching for custom JS.
- **`surface.inverse` added 2026-07-22** (`{color.gray.900}`) — the one dark surface role in this otherwise light-themed system, added specifically for Tooltip's background. Pair with `text.onFill`/`icon.onFill`, not `text.default`. Not a "dark mode" token — scoped to small inverse-context UI.
- **Tooltip has an arrow after all** — the initial "no arrow, checked against Linear/Vercel" call got reversed once built and seen live: without one, the tooltip read as ambiguously floating rather than clearly pointing at its trigger. A small rotated-square `::after` (same bg as the bubble) fixed it. Lesson: some calls genuinely need to be seen live before they're trustworthy, not just reasoned about from references.
- **Every clickable element in a component demo needs real interactive states, even a small close (×) button** — Popover/Drawer/Modal's close buttons and Drawer/Modal's footer actions first shipped with zero hover/focus feedback (Popover close) or ad-hoc throwaway CSS that didn't match the design system at all (Drawer/Modal's `.demo-trigger`, plain border-box buttons with none of Button's actual colors). Fixed by giving every one of them the real recipe: close buttons ARE Button ghost sm icon-only (32×32, 16px icon) — size, radius, colors and ring resolved from `button.tokens.json` in each builder (was a hand-sized 28px/18–20px copy until 2026-09-30; the component-local `closeIcon` tokens went with it); footer actions use `fill.neutral`/`fill.primary`/`fill.danger` + their `*Hover`/`*Active` siblings, `radius.default`, `dim.10` height — Button's actual semantic recipe, not a look-alike. If a demo has something clickable, it is not decoration — style it for real.
- **Section dividers need to span the full width on big edge-attached/floating panels, not sit inset within shared padding** — Drawer/Modal's header/footer border-bottom/border-top first lived inside one shared-padding `.content` wrapper, so the divider stopped short of the panel's actual edges — looked misaligned at that scale (unlike Card, where an inset divider is fine — small surface, reads as intentional). Fixed by making header/body/footer each their own full-width band with its own padding; the divider sits on the section itself, spanning edge to edge. If a future component has multiple stacked sections and is bigger than Card, check whether its dividers reach the true edges before calling it done.
- **Header/footer being optional needs an explicit body-only example, not just a description line** — showing only the fully-composed (header+body+footer) version made Drawer/Modal look like they *require* that structure, same trap Card originally fell into before its own "Body only" story got added. Any component with optional composable sections should demonstrate the minimal case, not just describe it as optional in prose.
- **`showModal()` gives Escape-to-close and focus-trap for free, but NOT click-outside-to-close** — a real gap the body-only Drawer/Modal example exposed immediately (no header close button, no footer Cancel, and without this fix, no way to dismiss short of Escape). Fixed with the standard MDN light-dismiss recipe: since the dialog's own padding is 0 and its `__content` wrapper fills 100% of it, a click landing on the `<dialog>` element itself (not a descendant) can only mean it hit the backdrop — `if (e.target === dlg) dlg.close()`. Applies to Drawer and Modal both; Popover doesn't need this, the native `popover` attribute already includes outside-click dismissal.
- **Orient component-boundary decisions toward how downstream developers will actually consume this (real Tailwind/React ports), not toward what's convenient for this repo** — user's explicit correction 2026-07-22: initially proposed one blended "Dropdown" component covering both action-menu and selectable-option content (simpler to build here, since this project doesn't implement real keyboard nav/ARIA anyway). Reversed after the user pointed out that real component libraries (Radix etc.) split these because the underlying ARIA roles/keyboard models genuinely differ (menu/menuitem vs. listbox/option) — and this design system's whole point is to set the boundary real implementations will inherit, so getting it right now avoids a painful re-split later once actual devs are wiring it up. Resulted in Menu and Listbox as separate components. Apply this lens generally: "easiest for the static-docs generator" and "correct primitive boundary for a real port" aren't always the same answer, and the second one wins.
- **AlertDialog established the pattern for a zero-new-token behavioral variant**: same visual tokens as its base component (Modal), differing only in which scripts attach — a `data-alert` marker attribute lets the shared dismiss-script `if`-branch skip it, plus one extra listener (`cancel` event + `preventDefault()`) blocks Escape. No new color/dimension/typography tokens, no separate CSS beyond what the base component already has. Reuse this shape (marker attribute + script branching, not a token fork) for any future "same look, stricter behavior" variant.
- **`avatar.*` semantic group added 2026-07-22** (`tokens/semantic/color.tokens.json`) — 8 identity hues (bg @ 100 / text @ 600, same hue order as `chart-series` for a consistent categorical rhythm) for Avatar's initials fallback. Deliberately its own token set, not a reuse of `chart-series` (that sits at the 500 step, tuned for saturated lines/bars on a plot, not a pastel fallback badge) and not the 4 semantic role colors (`bg.primary/success/danger/warning` — reusing e.g. `bg.danger` for "this happens to be Jane's fallback color" would visually read as an error state on Jane's avatar, wrong meaning entirely). This is also the first semantic group with a **nested** shape (`avatar.hue.bg`/`avatar.hue.text` instead of one flat `name.key`) — `build-semantic-colors-doc.mjs`'s `renderGroup()` was generalized to walk down to whichever depth actually holds a `$value` instead of assuming every group is flat; check that helper still works if a future group nests differently.
- **`resolveToken()` silently drops `$extensions`** (the field `text-style.link-sm`/`label-sm`/etc. use for `textDecoration`/`textTransform`) — it only ever reads a token's `.$value`, so a typography ref resolved through the normal helper loses that data with no error, no missing-key warning, nothing. Listbox's "Clear all" link first rendered with no underline because of exactly this. Fix: fetch `$extensions` directly from the referenced node (`get(ref).$extensions`) rather than trusting the resolved typography object to carry it. **Recurred a second time on Message's body links (2026-07-22)** — caught before shipping this time (checked, not assumed), but only because a real `<a>` tag's own browser-default underline happened to visually mask the missing CSS; a `<span>`/`<button>` standing in for a link would have shown the bug immediately, the way Listbox's did. Check any future component using `link-*`/`label-*` text-styles for the same silent gap — `counter.tokens.json` also references `label-sm`/`label-base` and still hasn't been explicitly verified against this failure mode.
- **`tag.*` semantic group added 2026-07-22** (`tokens/semantic/color.tokens.json`) — 10-hue decorative categorical palette for Badge's `color` axis (generic tagging, unrelated to status meaning), each hue with `tint` (100/600, mirrors `bg.*`/`text.*`) and `solid` (500 + `text.onFill`, mirrors `fill.*`/`text.onFill`). 5 of the 10 hues (gray/blue/red/green/amber) are pure aliases of the existing neutral/primary/danger/success/warning role tokens — deliberately, so `color="blue"` and `role="primary"` render identically rather than shipping two subtly-different blues. Only orange/violet/magenta/teal/brown are genuinely new leaf references. **Tint+solid as a paired fill axis, applied consistently across both a component's semantic *role* and its decorative *color*, is now the established shape for any future "small colored pill/chip" component** (Chip is next in line and should follow it) — don't invent a third intensity or a different pairing convention without a real reason.
- **Two-axis "role vs. color" split, never combined, established by Badge 2026-07-22**: a component can have a small set of *meaningful* states (`role`) reusing the system's own semantic colors, and separately a larger set of *decorative* options (`color`) for generic categorization, but a single instance picks one axis or the other, never both at once. Apply this same split to any future component that needs both "this means something" and "this is just a color I picked" (e.g. Chip's own color options, if it ever needs them).
- **"Live product outranks aspirational mockup" — the standing tie-breaker for the whole Message/Bubble/Attachment family, established on Message and reused consistently through the rest of it**: whenever the real Message Center screenshots and the staff-mobile mockups disagreed on how something should look, the live product's own behavior won as the default, and the mockup's version got documented as a secondary/optional variant rather than silently dropped. Applied on Message (chrome: none, not the mockup's white bubble), Bubble (self defaults to a pale tint, not the mockup's solid blue), and — the one deliberate exception, called out explicitly rather than applied blindly — ThreadListItem's Expires value, where neither side simply won: kept the live app's row/label *structure* but upgraded the specific value to a real Badge instead of either bare red text or a full mockup-style pill. The lens is "default to the live product," not "always literally copy the live product" — check whether a newly-available proper component (like Badge) should replace what the live app was improvising with before assuming the live app's exact implementation is the target.
- **`ai` semantic role added 2026-07-22** (`bg.ai`/`fill.ai`/`fill.aiHover`/`text.ai`/`icon.ai`, `tokens/semantic/color.tokens.json`) — violet, for Composer's AI Assist button. Same bar `surface.inverse` was added under: a genuine cross-product need (Message Center's composer and the future AI chat product both want one consistent "this is the AI feature" accent), not spec'd speculatively — the immediate consumer (Composer) needed it the same session it was added. violet was picked because it was already an unused-as-semantic-role primitive family; none of the 4 existing status roles (primary/success/danger/warning) mean "AI", so reusing one would misattribute the feature. Rest state uses the `bg.ai` tint (mirrors Badge's tint recipe); hover adds a `fill.ai` border (mirrors Chip's unchecked-hover / Card's own hover "border previews the role color" language) — no new hover-shade invented.
- **6 new Material icons sourced 2026-07-22 for Composer** (`format_bold`/`format_italic`/`format_underlined`/`local_offer`/`auto_awesome`/`send`, icon count now 142) — same method as the original icon-sourcing session: fetch the `src` subtree via the GitHub API by SHA (the plain recursive-tree call truncates before reaching `src`, confirmed again this time), confirm each real path (`{category}/{name}/materialicons/24px.svg` — filled style is just the bare `materialicons` folder, not a separate "filled" one), download via `raw.githubusercontent.com`, add `fill="currentColor"`. Icons land automatically in `docs/icons.html` on next rebuild — that page reads the asset folder directly (`fs.readdirSync`), no manual wiring needed beyond adding the files.

- **iOS bottom toolbar (2026-10-20, user)**: full-height panels on a phone (Assistant drawer, Browse Classes section sheet, the phone sidebar) are **pinned `top: 0; bottom: 0` (dialogs: `position: fixed; inset: 0 0 0 auto`), not `height: 100dvh`** — Safari's bottom toolbar hid their feet — and the CX shell's viewport meta has **`viewport-fit=cover`** so `env(safe-area-inset-bottom)` is real; every pinned foot pads by it (sheet foot, Assistant composer, sidebar account row). Other prototypes (Scheduling, MC…) still lack viewport-fit=cover — same fix when touched. **Round 2 (user's iPhone screenshots, iOS 26 Safari):** the bottom bar FLOATS over the page, so a panel pinned to the visible area ended above it and the dimmed page showed underneath. ## Known non-bugs (don't "fix" these again)

- **The in-app Browser preview doesn't run CSS transitions reliably** (seen 2026-10-15…20): a sliding drawer/sheet/sidebar measures and screenshots at its *starting* position long after it should have finished (computed `transform` still the from-value, `getAnimations()` empty). Setting `transition: none` on the element shows the real end state. Don't "fix" a drawer that looks stuck in a screenshot — check with transitions off first.

- `file://` preview in the Browser tool is flaky for this repo (outside the sandbox's recognized project root). Use a local HTTP server instead — see `CLAUDE.md`.
- The in-app Browser preview tool's `screenshot` action is also unreliable on tall pages after scrolling far down (returns a blank capture even via `http://`, even after a wait) — a tool-level rendering/sync glitch, not a page bug.
