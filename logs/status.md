## Locked-in conventions (don't relitigate these without reason)

- **Fill+border on form fields** (Input/Select/Search): `surface.sunken` bg + `border.default` hairline, strengthening to `border.strong` on hover, `border.focus` (blue) on focus. Not a pure outline or pure fill — evidenced by those tokens' own `$description`s, written before any component existed.
- **Ghost/ghost-like hover progression**: transparent (rest) → `fill.neutralHover` (hover) → `fill.neutralActive` (press/active). Used identically by Button ghost, Pagination page-items, Tabs (both styles, including underline's hover background — text-color-only hover was tried and found too subtle).
- **Disabled usually keeps the same background as default**, only text/icon fade to `*.disabled` — because `fill.disabled` / `surface.disabled` / `fill.neutral` / `surface.sunken` are all literally `{color.gray.100}`. Confirmed intentional, not a bug, recurred across Button secondary, Input, Select, Search.
- **CSS custom properties**: every resolved color is `--tok-<dotted-path-kebab>` (e.g. `fill.primaryHover` → `--tok-fill-primary-hover`), generated by `tools/lib/css-vars.mjs`. The `--tok-` prefix is load-bearing — without it a token can collide with the docs chrome's own `--text-primary`/`--border`/`--accent` (happened once, turned page text blue).
- **BEM**: shared block class (`.btn`, `.input`, `.select`, `.search`, `.tab`, `.counter`, `.page-item`, `.separator`) + `--modifier` for size/variant/state + `__element` for icon/label sub-parts. Where two variants share 100% identical sizing (Button primary/secondary/ghost; Tabs segmented/underline), the size grid is asserted identical at build time (`primarySizes.forEach(...) throw if diverged`) rather than trusted blindly — DTCG can't alias a whole sub-tree so the JSON duplicates the values, the assertion is the safety net.
- **Reused sub-components must resolve real values, never retype color-role names by hand** — caught two real bugs (Tabs' counter, both the wrong token guessed and a missing icon-disabled override) exactly from skipping this.
- **No hard caps on repeating collections** (Pagination pages, Tabs count) — `overflow-x: auto` + a practical guideline in the legend, confirmed with the user as the preferred approach over a hard-coded limit.
- Every docs page prints the *exact* generated CSS string both live and as the "copy this" code sample — one source, can't drift. Icons in printed code samples are `<!-- icon: name --></svg>` placeholder comments, not full path data.
- Radius is `radius.default` (8px) everywhere unless there's a specific reason otherwise (e.g. Tabs' `radius.md` track with a deliberately nested `radius.default` pill). **Concentric-radius rule for when a rounded shape sits flush inside another rounded shape** (touching edges, like Tabs' pill inside its track): `inner radius = outer radius − padding between them`, or equivalently `outer = inner + padding` — otherwise the two curves don't share a center and the gap looks uneven/bulging even with identical padding on all sides. Only relevant when one rounded shape is actually nested directly inside another (researched 2026-07-22) — a plain Card sitting on the page isn't nested in anything rounded, so it just uses `radius.default` with no extra math. Will matter for Modal/Drawer panel-inside-overlay later.
- **No implicit "default" padding value on Box** — confirmed against Chakra/MUI's own Box (2026-07-22 research): neither gives Box an implicit padding, always an explicit token choice, because unlike Button's height (one genuinely privileged size, used ~90% of the time) there's no single "right" padding for a generic container — it's entirely contextual (a chip vs. a section). Box's `none/xs/sm/md/lg` padding steps stay equally-weighted on purpose, no step singled out as "the" default. (Card, being one fixed *opinionated* composition rather than a generic primitive, is correctly the one that does have one fixed padding — `dim.4`.)
- **Native `<input>` for Checkbox/Radio**, visually hidden (clip-rect technique, not `display:none`) — keyboard/forms/screen readers/`:indeterminate` all work for free, only the paired `<span>` box/circle is repainted via `~` sibling selectors off `:checked`/`:disabled`/`:focus-visible` on the real input. Checkmark/dash glyphs reuse the shared Material icon set (`check.svg`/`remove.svg`), not bespoke assets.
- **`border.primary`/`border.success`/`border.danger`/`border.warning` are pale 200-tint roles, not brand-strength** — `border.primary` (blue.200, `#b2d4fe`) is much lighter than `fill.primary` (blue.500, `#077fec`). Radio's checked state first used `border.primary` for the ring, pairing a washed-out ring with a saturated dot — looked broken, caught before shipping. Fixed to reuse `fill.primary` for both ring and dot (same pattern Checkbox's checked state already uses for bg+border). `border.danger` at Input/Select error *is* the pale tint used correctly (a hairline-weight error border, not an emphasis border) — don't assume every `border.*` role is interchangeable with its same-named `fill.*`/`icon.*` counterpart; check the resolved hex before reusing one for emphasis.
- **No shadow/elevation token family exists anywhere in this system** — every surface (Input/Select/Search fields, now Card) draws separation with a `border.default` hairline, never a drop shadow, matching the flat Linear/Stripe-Dashboard/Notion aesthetic `typography.tokens.json`'s own `$description` names as the explicit reference. Card was built border-only on purpose, not because shadow was forgotten — don't introduce a shadow primitive for one component without a real cross-component need (e.g. a floating/overlay component that genuinely needs to look "lifted" off the page, unlike a page-level content Card).
- **Prefer white/default surface + hairline borders over stacking multiple gray tint layers for hierarchy** (e.g. gray page → grayer card → white inner card). User's prior design habit was layered depth via progressively darker/lighter grays (sometimes 3 levels); explicit call **2026-07-22**: favor a cleaner look for this system, closer to Linear/Stripe/Notion, and lean on `border.default` (or spacing/radius) to separate sections *before* reaching for a second surface tint. `surface.sunken` stays reserved for genuinely recessed elements (Input/Select/Search fields) — don't reach for it as a general "nested container" background. This is a default lean, not an absolute ban: a deliberate gray-card-on-gray-page case is still fine when a screen genuinely needs that grouping — just shouldn't be the reflex choice for every new panel/section.
- **Always render every state-dependent glyph/element in the markup, hidden via CSS, rather than conditionally injecting it at build time** — Checkbox's check/indeterminate icons were first only inserted into the HTML when the *doc-build script* had that item pre-checked; any live checkbox a user actually clicked (e.g. in the CheckboxGroup demo) had no icon element in the DOM at all, so clicking it just turned the box solid blue with no tick inside. Fixed by always emitting both glyphs with `display:none`, shown only via `:checked`/`:indeterminate` on the real sibling input — the same "let the real cascade drive it" principle already used for background/border color. Check any future component with build-time-conditional markup for the same trap.
- **`border.focus` is `{color.blue.600}` (not 500), ring width is `{dim.1}` = 4px (not `dim.0_5`/2px) — system-wide, affects every component with a focus ring/border** (Button, Input, Select, Search, Checkbox, Radio, Tabs, Card). Changed **2026-07-22** while designing Card's interactive hover/pressed: once hover/pressed started using `fill.primary` (blue.500) for a stronger, more visible cue, focus needed to move up a step too so keyboard focus stays unambiguously the *strongest* state — mouse hover is the common case but focus is the accessibility-critical one (a keyboard/switch user has no other way to see where they are), so it must out-rank hover, not just differ from it. Don't reset this back to 500/2px without re-checking every component's ring, not just Card's.
- **Unchecked-hover on Checkbox/Radio is also `fill.primary` now, not `border.strong`** — same "gray reads as too weak a cue" lesson from Card, applied consistently (2026-07-22). And for the checked+hover combination specifically, reuse `fill.primary`→`fill.primaryHover` (blue.500→600) — the *exact same pair* Button primary already uses for its own fill→hover darkening — rather than inventing a new darkening step. General pattern worth remembering: when a control's "on"/filled state needs a hover-darken, check whether the semantic layer already has a `*Hover` sibling for that fill role before creating anything new (it usually does — `fill.primaryHover`/`successHover`/`dangerHover`/`warningHover`/`neutralHover` all already exist).
- **Shadow/elevation tokens: introduced 2026-07-22** (`tokens/primitives/shadow.tokens.json`, 3 steps: sm/md/lg), exactly when the overlay family got built, per the plan flagged earlier — scoped deliberately to Tooltip/Popover/Drawer/Modal only. Every other surface (Input/Select/Search fields, Card) still draws separation with `border.default`, never a shadow — don't reach for `shadow.*` outside the floating-UI family without a genuinely new floating component to justify it.
- **Overlay components use native browser mechanisms, not hand-rolled JS state** — Tooltip is pure CSS (`:hover`/`:focus-within`); Popover uses the native `popover`/`popovertarget`/`popovertargetaction` HTML attributes (Popover API); Drawer/Modal use `<dialog>`+`showModal()`. All four get focus-trap/Escape/outside-click/top-layer stacking for free from the browser — zero JS for state management, only a small positioning script for Popover and a one-line `showModal()` call for Drawer/Modal (dialogs have no declarative "open" attribute the way Popover has `popovertarget`). Close buttons use `<form method="dialog">`, not `onclick` handlers. Follow this same native-first approach for any future overlay-ish component (e.g. Select's dropdown) before reaching for custom JS.
- **`surface.inverse` added 2026-07-22** (`{color.gray.900}`) — the one dark surface role in this otherwise light-themed system, added specifically for Tooltip's background. Pair with `text.onFill`/`icon.onFill`, not `text.default`. Not a "dark mode" token — scoped to small inverse-context UI.
- **Tooltip has an arrow after all** — the initial "no arrow, checked against Linear/Vercel" call got reversed once built and seen live: without one, the tooltip read as ambiguously floating rather than clearly pointing at its trigger. A small rotated-square `::after` (same bg as the bubble) fixed it. Lesson: some calls genuinely need to be seen live before they're trustworthy, not just reasoned about from references.
- **Every clickable element in a component demo needs real interactive states, even a small close (×) button** — Popover/Drawer/Modal's close buttons and Drawer/Modal's footer actions first shipped with zero hover/focus feedback (Popover close) or ad-hoc throwaway CSS that didn't match the design system at all (Drawer/Modal's `.demo-trigger`, plain border-box buttons with none of Button's actual colors). Fixed by giving every one of them the real recipe: close buttons are a small (28px) ghost icon-button (transparent → `fill.neutralHover` → `fill.neutralActive` → focus ring, exactly Button ghost icon-only's own pattern); footer actions use `fill.neutral`/`fill.primary`/`fill.danger` + their `*Hover`/`*Active` siblings, `radius.default`, `dim.10` height — Button's actual semantic recipe, not a look-alike. If a demo has something clickable, it is not decoration — style it for real.
- **Section dividers need to span the full width on big edge-attached/floating panels, not sit inset within shared padding** — Drawer/Modal's header/footer border-bottom/border-top first lived inside one shared-padding `.content` wrapper, so the divider stopped short of the panel's actual edges — looked misaligned at that scale (unlike Card, where an inset divider is fine — small surface, reads as intentional). Fixed by making header/body/footer each their own full-width band with its own padding; the divider sits on the section itself, spanning edge to edge. If a future component has multiple stacked sections and is bigger than Card, check whether its dividers reach the true edges before calling it done.
- **Header/footer being optional needs an explicit body-only example, not just a description line** — showing only the fully-composed (header+body+footer) version made Drawer/Modal look like they *require* that structure, same trap Card originally fell into before its own "Body only" story got added. Any component with optional composable sections should demonstrate the minimal case, not just describe it as optional in prose.
- **`showModal()` gives Escape-to-close and focus-trap for free, but NOT click-outside-to-close** — a real gap the body-only Drawer/Modal example exposed immediately (no header close button, no footer Cancel, and without this fix, no way to dismiss short of Escape). Fixed with the standard MDN light-dismiss recipe: since the dialog's own padding is 0 and its `__content` wrapper fills 100% of it, a click landing on the `<dialog>` element itself (not a descendant) can only mean it hit the backdrop — `if (e.target === dlg) dlg.close()`. Applies to Drawer and Modal both; Popover doesn't need this, the native `popover` attribute already includes outside-click dismissal.
- **Orient component-boundary decisions toward how downstream developers will actually consume this (real Tailwind/React ports), not toward what's convenient for this repo** — user's explicit correction 2026-07-22: initially proposed one blended "Dropdown" component covering both action-menu and selectable-option content (simpler to build here, since this project doesn't implement real keyboard nav/ARIA anyway). Reversed after the user pointed out that real component libraries (Radix etc.) split these because the underlying ARIA roles/keyboard models genuinely differ (menu/menuitem vs. listbox/option) — and this design system's whole point is to set the boundary real implementations will inherit, so getting it right now avoids a painful re-split later once actual devs are wiring it up. Resulted in Menu and Listbox as separate components. Apply this lens generally: "easiest for the static-docs generator" and "correct primitive boundary for a real port" aren't always the same answer, and the second one wins.
- **AlertDialog established the pattern for a zero-new-token behavioral variant**: same visual tokens as its base component (Modal), differing only in which scripts attach — a `data-alert` marker attribute lets the shared dismiss-script `if`-branch skip it, plus one extra listener (`cancel` event + `preventDefault()`) blocks Escape. No new color/dimension/typography tokens, no separate CSS beyond what the base component already has. Reuse this shape (marker attribute + script branching, not a token fork) for any future "same look, stricter behavior" variant.
- **`avatar.*` semantic group added 2026-07-22** (`tokens/semantic/color.tokens.json`) — 8 identity hues (bg @ 100 / text @ 600, same hue order as `chart-series` for a consistent categorical rhythm) for Avatar's initials fallback. Deliberately its own token set, not a reuse of `chart-series` (that sits at the 500 step, tuned for saturated lines/bars on a plot, not a pastel fallback badge) and not the 4 semantic role colors (`bg.primary/success/danger/warning` — reusing e.g. `bg.danger` for "this happens to be Jane's fallback color" would visually read as an error state on Jane's avatar, wrong meaning entirely). This is also the first semantic group with a **nested** shape (`avatar.hue.bg`/`avatar.hue.text` instead of one flat `name.key`) — `build-semantic-colors-doc.mjs`'s `renderGroup()` was generalized to walk down to whichever depth actually holds a `$value` instead of assuming every group is flat; check that helper still works if a future group nests differently.
- **`resolveToken()` silently drops `$extensions`** (the field `text-style.link-sm`/`label-sm`/etc. use for `textDecoration`/`textTransform`) — it only ever reads a token's `.$value`, so a typography ref resolved through the normal helper loses that data with no error, no missing-key warning, nothing. Listbox's "Clear all" link first rendered with no underline because of exactly this. Fix: fetch `$extensions` directly from the referenced node (`get(ref).$extensions`) rather than trusting the resolved typography object to carry it. Check any future component using `link-*`/`label-*` text-styles for the same silent gap — `counter.tokens.json` also references `label-sm`/`label-base` and was never verified against this specific failure mode.

## Known non-bugs (don't "fix" these again)

- Component doc pages don't `<link>` the real Sora font file (only `typography.html` does) — falls back to system sans-serif. Sometimes renders slightly slanted in the sandboxed preview browser specifically; not reproducible as a real CSS `font-style` issue (checked via computed styles). Pre-existing since Button was first built, consistent across all pages.
- `file://` preview in the Browser tool is flaky for this repo (outside the sandbox's recognized project root). Use a local HTTP server instead — see `CLAUDE.md`.
